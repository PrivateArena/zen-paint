## Commit Review: `1dcbea3`

### ✅ Tokenizer (`internal/tokenizer/tokenizer.go`) — Good

The CLIP BPE tokenizer is correctly implemented: it replicates the OpenAI BPE algorithm with the proper byte-to-unicode mapping (`bytesToUnicode()`), greedy pair merging, the right regex for pre-tokenization, and SOT/EOT tokens. This matches HuggingFace's `CLIPTokenizer` behavior faithfully.

The T5 tokenizer uses a greedy longest-match approach, which is a reasonable approximation for inference. It's not true SentencePiece (which uses the Unigram algorithm), but it will produce sensible token IDs for most prompts, which is a large improvement over raw bytes.

**One real bug to fix:** In `bytesToUnicode()`, the Latin-1 ranges use byte-cast arithmetic that breaks in Go because bytes are unsigned and the string `"¡"` to `"ÿ"` are multi-byte in UTF-8. For example, `'¡'` as a Go `rune` is `0xA1` (161), but iterating `for b := int('¡'); b <= int('¬')` in a `byte` loop will not behave as you expect — `b2u[byte(b)]` silently truncates values above 127 back to lower bytes, creating silent mapping collisions. The reference Python implementation uses explicit ranges `[33..126, 161..172, 174..255]` over raw byte values 0–255. Your implementation is close but the range loops for the Latin supplement block should use integer literals, not rune literals:

```go
// ❌ Current — rune('¡') is 0xA1 = 161, fine, but byte(161) wraps correctly... 
// actually works on little-endian, but is confusing and fragile
for b := int('¡'); b <= int('¬'); b++ { b2u[byte(b)] = rune(b) }

// ✅ Safer — be explicit
for b := 161; b <= 172; b++ { b2u[byte(b)] = rune(b) }
for b := 174; b <= 255; b++ { b2u[byte(b)] = rune(b) }
```

The logic happens to produce the right output in practice since Go's `rune` cast of ASCII-range Latin-1 values fits in a byte, but it's fragile and worth fixing.

**Minor:** The `Encode` path for CLIP lowercases the input (`strings.ToLower`) but the reference CLIP tokenizer does **not** lowercase by default — it's case-insensitive via the regex but preserves case for BPE encoding. This is unlikely to matter in practice since most vocab entries are lowercase, but worth noting.

### ✅ Hardware Acceleration (flux/sdxl `engine.go`) — Good

The execution provider switch is correctly placed (before session creation), gracefully falls back to CPU on failure, and covers all four requested providers. The ROCm path using `AppendExecutionProvider("ROCM", ...)` is the right generic API for `onnxruntime_go`.

**One issue in the CUDA block** (same pattern in both `flux` and `sdxl`):

```go
// ❌ Bug: shadows the outer `err` variable from Initialize's scope
cudaOpts, err := ort.NewCUDAProviderOptions()
if err == nil {
    defer cudaOpts.Destroy()
    err = sessOpts.AppendExecutionProviderCUDA(cudaOpts)
}
if err != nil {  // ← this checks the inner err, not the outer one
```

The `:=` on `cudaOpts, err` creates a new `err` scoped to the `case` block. If `NewCUDAProviderOptions()` fails, the outer `err` from `Initialize` is untouched, but the `if err != nil` check below it refers to the inner one, so the fallback warning prints correctly. However, if `AppendExecutionProviderCUDA` fails, the inner `err` is set but the outer `err` still holds whatever it was before. This works by accident. Change `cudaOpts, err :=` to `cudaOpts, cudaErr :=` and use `cudaErr` throughout that case block for clarity and safety.

### ✅ Tests — Good coverage, one race condition

The server test correctly validates all three things (status, static serving, 429 concurrency). The 20ms sleep to "ensure first request has entered the semaphore" is a **test race condition** — on a loaded CI machine, 20ms might not be enough. A more robust approach would use a `sync.WaitGroup` or channel in the mock engine to signal when it's inside `Generate` before firing the second request.

The tokenizer test only validates the fallback path and basic shape — it doesn't verify actual BPE output against known-correct token IDs (the plan mentioned matching HuggingFace canonical outputs). That's the more important test to eventually add.
